## Context

`User.realName` 是比對同一人的主要線索，但系統上無唯一限制，也沒有任何既有查詢會跨帳號比對它。`isUndeliverableEmail`（`lib/mailer.ts:29`）已能判定 email 是否為 `@seed.iwillshare.org.tw` 合成信箱，`getMemberDisplayName`（`lib/utils/member-display.ts`）已是既有的顯示名稱推導邏輯。機敏欄位（電話、Email）在後台一律預設遮蔽、點擊切換明文（`admin-sensitive-masking` spec），本頁的並排欄位需沿用同一元件 `MaskedValue`（`components/admin/masked-value.tsx`），不得自行另寫明文顯示。

既有「未啟用會員」頁面（`app/[locale]/(admin)/admin/members/inactive/page.tsx`）與其資料層（`lib/data/account-recovery.ts`）是最接近的既有範例：server component 直接 await 資料層查詢、純表格呈現、`MemberHomeLink` 連回會員公開頁。本功能的頁面結構直接比照它。

## Goals / Non-Goals

**Goals:**
- 盤點全站會員中，`realName` 相同且至少命中一項輔助訊號的配對，依信心分級呈現。
- 讓管理者能在同一畫面並排看到兩邊關鍵欄位，快速判斷是否為同一人。
- 作為 CR-FEAT-261016-003（合併帳號精靈）的候選來源與驗證基礎。

**Non-Goals:**
- 不做任何合併、刪除、編輯等寫入操作（留給 CR-FEAT-261016-003）。
- 不處理 `realName` 為空的會員之間的比對（系統上另有 22 筆姓名空白的既有資料問題，由 CR-FEAT-261016-001 處理根因，不在本次範圍內）。
- 不做模糊比對（同音異字、暱稱比對）；僅做精確字串相等比對，避免誤判率過高。
- 不新增資料庫欄位、不新增索引。

## Decisions

- **分組演算法：先依 `realName` 精確分組，組內才兩兩配對分級，不做全表 O(n²) 掃描。**
  理由：所有三個信心等級都要求 `realName` 相同，先用一個 `Map<realName, User[]>` 分組，只在同名組（size ≥ 2）內做組合，計算量與同名組大小成正比，現有會員規模（數百～數千筆）下可一次查詢、記憶體內運算完成，不需要資料庫層的複雜查詢或索引調整。
- **只取 `realName` 非空者參與分組。**
  理由：姓名空白的帳號彼此比對沒有意義（會因為「都是空字串」而全部互相命中），且該類資料另有 CR 處理根因。
- **信心分級判斷順序：先判最高（seed 信箱），再判高，再判中；一組配對只取最高命中的等級，不重複列多筆。**
  理由：同一組配對若同時命中「seed 信箱」與「phone 相同」，只需要呈現一次、取最具鑑別力的等級，避免清單重複與管理者混淆。
- **每組配對之候選兩邊都帶出「是否未啟用」「報名/結業紀錄筆數」等輔助欄位，但不納入分級計算本身。**
  理由：這些欄位是給管理者肉眼判斷用的輔助資訊（例如一邊有大量結業紀錄、一邊剛建立不久，大概率是誤判），分級本身維持 proposal 定義的三條規則，不額外加權，避免規則複雜化難以說明。
- **機敏欄位沿用 `MaskedValue`，不新增獨立的遮蔽邏輯。**
  理由：比照既有 `admin-inactive-members` 頁面做法，保持全站機敏欄位遮蔽行為一致。
- **頁面為獨立路由 `/admin/members/duplicates`，不做成 `/admin/members` 頁內 tab。**
  理由：比照現有「未啟用會員」做法（獨立路由 + 後台首頁卡片入口），該頁本身查詢邏輯與會員清單頁無關，獨立路由可各自 `force-dynamic`、互不影響快取策略。
- **資料層獨立新檔 `lib/data/duplicate-accounts.ts`，不塞進 `lib/data/account-recovery.ts`。**
  理由：`account-recovery.ts` 的查詢範圍是「找回帳號」流程與未啟用會員清單，語意上是單一帳號查詢；本功能是跨帳號配對比對，關注點不同，獨立檔案較清楚，未來若要給 CR-FEAT-261016-003 的合併精靈重用分級邏輯時也方便直接 import。

## Risks / Trade-offs

- [常見姓名（如單姓單名）可能大量誤判為「中」信心度配對，造成清單噪音] → 分級本身已把「僅姓名相同」排除在三個等級之外（中等以上都要求至少一項輔助訊號），且清單依信心排序，管理者可優先處理「最高」「高」等級，「中」等級本就是較低優先的參考。
- [`realName` 可能存在全半角、空白差異造成明明是同一人卻比對不到] → 本次僅做精確字串相等比對（Non-Goal 已排除模糊比對），若實測發現大量漏判，留待後續 CR 再評估正規化規則，不在本次處理。
- [配對基數隨會員數成長，若未來會員規模大幅增加，記憶體內兩兩配對可能變慢] → 現有規模下可接受；若日後規模顯著變大，可在資料層查詢階段先過濾掉明顯不可能的（例如用 SQL `GROUP BY realName HAVING COUNT(*) > 1` 先篩出有重複姓名的組），本次不預先處理。

## Migration Plan

- 無資料庫 schema 變更，純新增唯讀頁面與資料層查詢函式。部署即生效；回退只需移除新路由與後台首頁卡片項目，不影響任何既有功能或資料。
