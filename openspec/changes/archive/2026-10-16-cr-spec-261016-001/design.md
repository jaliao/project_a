## Context

原規劃透過「批次寄送提醒信」要求帳號本人登入補資料，但這 22 筆帳號本來就是自助索取臨時密碼註冊後長期未登入才會落入此清單，寄信無法保證本人會配合登入補資料，且管理者仍須後續人工追蹤回補率。改用「直接回填」可立即解決清單顯示問題，不依賴本人配合、不留下需要追蹤的半成品狀態。

顯示名稱邏輯見 `lib/utils/member-display.ts` 的 `getMemberDisplayName`：優先序為 `nickname` → `realName` → `englishName`，三者皆空時顯示「（未填）」。

## Goals / Non-Goals

**Goals:**
- 讓這 22 筆帳號不再顯示「（未填）」。
- 不須等待本人登入、不須管理者後續人工追蹤。
- 本人日後登入後仍可自行於 Profile 修改為真實姓名——回填值僅為暫時識別用途，非強制鎖定。

**Non-Goals:**
- 不做成可重複使用的後台「自動回填」功能或排程（本次僅處理已知的 22 筆 id，非一般規則；未來若再出現同類情況，屬於另一次查證與決策，不應該被本次程式碼自動套用）。
- 不處理已登入過但姓名仍空白的會員（狀況不同，不在本次範圍）。
- 不保留先前已實作的批次提醒信功能——整個撤回，日後若有需要再重新評估與開發。

## Decisions

- **回填值來源：email `@` 前的原始字串，不做任何猜測性加工（不拆字、不轉大小寫、不去除數字）。**
  理由：這批帳號 email 本身多半看不出真實姓名（如 `123@gmail.com`、`a0968708712@gmail.com`、`1234@test.com`），嘗試智慧解析（例如猜測英文姓名拆字、去除尾端數字）在資料品質參差的情況下不可靠，容易做出錯誤或各帳號規則不一致的猜測；保留原始字串最忠實、可預期、可重現，且執行前已列出完整清單供人工核對。
- **`nickname`／`realName`／`englishName` 三欄皆填同一值，而非只填其一。**
  理由：顯示名稱優先序是 `nickname` → `realName` → `englishName`；三欄一致可避免因 `displayNameMode` 設定不同而出現顯示不一致的情況，且不影響本人之後只改其中一欄的使用彈性。
- **直接以一次性 SQL／腳本在正式環境執行，不開發後台 UI 功能。**
  理由：這是僅針對已知 22 筆 `id` 的操作，不具重複使用價值（不是「每次遇到未啟用會員都要做」的一般規則），比起為一次性操作開發 UI/Server Action，直接執行更新風險更小、不留存未來可能誤用或誤觸的永久性程式碼。
- **撤回先前的「批次寄送提醒信」實作，不保留作為通用工具。**
  理由：使用者已決定改採直接回填，原方案不再對應任何使用情境；保留未串接任何觸發入口的程式碼只會造成維護負擔與誤導（看起來像現行功能、實際未被使用）。日後若真的需要「提醒未登入會員」的功能，屆時依當下情境重新設計更合適。

## Risks / Trade-offs

- [回填值多為無意義字串（如 `123`、`a0968708712`），並非真實姓名] → 已在 proposal 中明確說明這只是暫時識別用途；本人登入後可自行於 Profile 修改為真實姓名，不影響帳號其他功能。
- [直接寫入正式資料庫，操作本身不可逆（除非再次手動回填）] → 執行前以唯讀查詢列出完整清單（email + 推算值）供人工確認，確認後才執行 UPDATE；以明確的 22 筆 `id` 限定更新範圍（而非模糊條件如「姓名皆空」），避免執行當下若有其他新進資料符合同樣條件而被誤改。

## Migration Plan

- 無 schema migration。資料修正以一次性腳本／SQL 直接對正式 DB 執行（鎖定本次查出的 22 筆 `id`），執行後以 SELECT 覆核結果（確認 22 筆皆已更新、無其他資料列受影響）。
