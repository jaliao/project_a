## 排查過程與發現

### 已排除的可能性

- **不是快取問題**：後台提問管理列表、學員提問頁、個人頁提問卡片皆為即時查詢 DB（`force-dynamic` 或因 `auth()` 而動態渲染），沒有任何 `unstable_cache`/`revalidateTag` 快取層
- **不是帳號被刪除連帶刪除**：徐正容的 `User` 帳號仍在，`createdAt` 為 2026-07-03，未被重建
- **不是 migration/部署造成的資料損失**：正式環境（GCP，見下）54 個 migration 全數為最新狀態，`support_inquiries` 相關 migration 早於 2026-07-22 就已套用完成，與本次事故無關
- **不是排程工作**：GCP 主機上沒有設定任何 crontab
- **不是應用程式碼問題**：全庫搜尋確認沒有任何刪除 `SupportInquiry` 的程式碼路徑（含 raw SQL / `$executeRaw`）
- **不是對外可利用的漏洞**：Postgres 僅 bind `127.0.0.1`，未對外開放；主機上未執行 Prisma Studio；要操作此 DB 必須先以 SSH key 登入該主機

### 一開始的誤判

排查初期，透過檢視 `support_inquiries` 資料表發現 id 序號有 3 個空缺（8、11、12；序號在 INSERT 失敗時仍會被消耗），加上同一時段的 container log 出現 3 次 Next.js Server Action 版本不符錯誤（`Failed to find Server Action ... This request might be from an older or newer deployment`，肇因於 2026-07-23 09:29 的容器重啟），因此最初推論為「提問從未真正寫入資料庫」。

**此推論後來被現場證人推翻**：Joyce、黃小鳥皆表示於當天下午（約 14:00 前）曾在後台「提問管理」實際看到這兩則提問內容，直到約 15:00–15:30 才消失。這代表資料**確實曾經成功寫入**，是之後才被移除，而非從未寫入。

### 確認的事實（正式環境查證，2026-07-24）

1. 正式環境實際運作在 **GCP 主機（`35.236.153.251`）**，而非 CLAUDE.md／Makefile 標示的 VPS3（`63.250.52.138`）——VPS3 上的 DB migration 停在 2026-07-03、資料停在 2026-07-16，是一顆已過時、未再使用的舊環境，非本次事故現場
2. GCP 正式站 `support_inquiries` 表目前共 10 筆，id 為 `1,2,3,4,5,6,7,9,10,13`，缺 8、11、12
3. 徐正容目前在 `support_inquiries` 查詢為 **0 筆**
4. Postgres 稽核紀錄不足：事故發生時 `log_statement=none`、`logging_collector=off`，資料庫層級沒有留下任何語句紀錄；後台 `admin_action_logs` 稽核表於事故時段（14:00–16:00）亦為 0 筆
5. 同一時段（13:55、14:47）app log 有 3 筆測試/種子帳號（`pa261185`／`87`／`88`）的臨時密碼信被判定為「合成 seed 信箱」而跳過寄送，代表當時有人對這些測試帳號執行了建立/重設密碼的操作；時間點與事故窗口接近，但**未找到與徐正容提問資料的直接關聯**，暫列為待釐清的旁支線索而非結論

### 根因結論

**資料的確被刪除**，但因正式環境當時未開啟 DML 層級的資料庫紀錄，且沒有 SQL 存取本身即會留痕的機制，**目前無法從系統面確認是誰、於何時、透過何種方式執行了這次刪除**。已排除應用程式本身的錯誤與已知的自動化流程。是否為人為透過 SSH 直接連線資料庫手動操作，仍待與可存取正式站主機的相關人員逐一確認。

## 已完成的補救措施（2026-07-24）

1. **開啟 Postgres DML 層級紀錄**：正式站執行 `ALTER SYSTEM SET log_statement = 'mod'` 並 `pg_reload_conf()`（已驗證：新增/刪除/更新語句皆會被記錄到 `docker logs postgres_db`），往後同類事故可直接追溯到實際執行的 SQL 語句
2. **新增 4GB swap**（`/swapfile`，已寫入 `/etc/fstab` 開機自動掛載；`vm.swappiness=10` 適合資料庫主機），緩解主機記憶體瞬間吃緊時直接觸發 OOM 的風險
3. **`docker-compose.yml` 新增記憶體限額**（`project-a-web`、`postgres_db` 各 `mem_limit: 3g` / `mem_reservation: 512m`），單一 container 記憶體暴衝時只會被 cgroup 限制在自己的邊界內重啟（兩者皆為 `restart: always`），不會再拖垮整台主機上的其他服務；變更已套用並驗證站台恢復正常（`https://activate.kuaglobal.org/` HTTP 200）

- **待確認**：需與所有持有 GCP 主機 SSH 存取權限的人員逐一確認，2026-07-24 14:00–15:30 是否有人手動連線資料庫執行過操作
